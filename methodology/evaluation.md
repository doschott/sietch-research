# Evaluation

Metrics for the sandbox study. Each metric is defined by the count the code actually keeps. Applying these definitions to logs from Dune: Awakening is **proposed, pending Funcom review**, and only if a written answer allows agent sessions at all.

## Units

- A **step** is one call to the mock world's `step`. A handoff that is accepted does not count as a step.
- A **failure** on a step is the first name in the observation's failure list. Extra names on that same step, such as `dehydration` beside another failure, stay on the observation and in the log, and do not open a second episode.
- A **failure episode** opens on the step where `observation.failure` becomes non-null while no episode is open. It stays open through later failing steps. It closes on the next step where `observation.failure` is null.
- **Recovery latency** for a closed episode is `close_tick - open_tick`. Ticks come from the world, which increments once per step.
- If the session ends while an episode is open, that episode adds nothing to the latency list and `unrecovered_failures` is 1. The counter tracks one open episode, so the flag is 0 or 1, not a count of every failed step.

Worked example from the replan fingerprint below: one `exposure` at tick 4, then a later step with no failure, latency 1, unrecovered 0.

## Metric definitions

| Metric | Definition |
| --- | --- |
| `steps` | Environment steps taken before the cap or the kill switch |
| `handoffs_accepted` | Complete handoff records applied to the assignment |
| `handoffs_rejected` | Records refused for missing fields, or refused as churn |
| Handoff accept rate | `handoffs_accepted / (handoffs_accepted + handoffs_rejected)` when the denominator is positive |
| `failures` | One entry per failing environment step: tick, failure name, agent, action |
| `recovery_latencies` | Latencies of closed failure episodes, in ticks |
| Total recovery latency | Sum of `recovery_latencies` |
| `unrecovered_failures` | 1 if an episode is still open at `session_end`, otherwise 0 |
| `approval_blocks` | High-impact actions denied by the gate |
| `killed` | True if the kill switch ended the loop |
| `final_water`, `final_base` | World values at the last observation |
| `final_owner`, `final_goal` | Assignment at `session_end` |

Handoff accept rate is undefined when no handoff was attempted. Scenario v1 always attempts at least one.

These metrics do not measure farming, wealth, combat score, or leaderboard position. Those are outside the request.

## Scenario v1 fingerprint

Locked by `scripts/tests/test_session.py::test_registered_scenario_orders_recovery`. Both runs use seed 7 and 16 steps. The numbers are properties of the scripted policies in the mock world. They are regenerated by the test. They are not measurements of a game.

| | Replan | Retry |
| --- | --- | --- |
| Steps | 16 | 16 |
| Handoffs accepted | 4 | 2 |
| Handoffs rejected | 0 | 0 |
| Failure names | one `exposure` | five `exposure` |
| Recovery latencies | `[1]` | `[2, 2]` |
| Unrecovered episodes | 0 | 1 |
| Total recovery latency | 1 | 4 |

H1 says the replan total (1) is lower than the retry total (4), and only the retry run ends unrecovered. The test fails if that fingerprint moves. A moved fingerprint is a change to the instrument. It is recorded in [deviations.md](deviations.md) if the plan changes with it. It is not a new scientific result by itself.

## What a pass means

- H2 passes when the minimal-handoff test rejects every incomplete record and leaves Eve as owner, and the default run accepts at least the four replan handoffs with zero rejections.
- H3 passes when a forced `discard_water` leaves water unchanged under the default approver, zeroes water only under an injected approving callback, a missing operator writes no log, and a kill during the run sets `killed` with `kill_switch` before `session_end`.

## What will not be reported as a finding

- Wall-clock time of a 16-step run
- The water and base totals, except as description of the episode
- Any comparison with published Minecraft or other game-agent scores
- Any statement about players, Funcom's servers, or Dune: Awakening balance

## Later metrics

If a stochastic world or a language-model policy is added, the analysis in [research-plan.md](research-plan.md) does not cover it. A new scenario id, a seed list, and a metric definition would be written first. **Proposed, pending Funcom review:** game-session metrics, if permission is granted, would be defined in that later addendum and would stay inside planning, handoff, and recovery. They would not be farm rates or leaderboard deltas.
